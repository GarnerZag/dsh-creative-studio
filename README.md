# 创意工坊 · Creative Studio

给 DeepSeek Harness 用的一个插件，专门干一件事：**在想法还糊着的时候，把「到底要做什么」聊明白，然后顺顺当当地交给开发。**

MIT License。

> 这是个开发预览版。功能齐了、测试也过了，但还没做过完整验收，别拿它存你唯一一份正式需求。真丢了我可赔不起。

## 为什么做这个

做产品最难受的时刻，不是写不出文档，是开会时所有人都点头、散会一动手发现各自想的是三件事。

而写文档这件事本身也劝退：需求一多就变成几十页 Word，没人读，改一版还要重发一遍。

所以我做了这么一个东西，把需求打磨的过程摊在屏幕上：想法、需求、架构、审批、交接，一步一步走，每一步都看得见、改得动、退得回。右边还挂着一个能点的 Demo —— 加一个功能，Demo 立马演给你看，而不是让你靠想象。

## 它怎么用（五步）

| 你在哪 | 你在做什么 | 屏幕上有什么 |
| --- | --- | --- |
| 想法 | 写一句模糊需求，一句话就够 | 我先复述一遍「我理解你要做什么」，把缺的信息、要你拍板的问题列出来。你确认了，我才往下走 |
| 需求 | 把需求理成一棵树 | 能拖的思维导图 + 大纲 + 右侧检查器；优先级、桌面/手机两套验收条件 |
| 架构 | 把需求翻成实现 | 模块 / 接口契约 / 技术决策 / 开发任务，四列依赖图 |
| 审批 | 冻结一版 | 版本差异（连改名、连某个字段的变化都标出来），可以只批准你勾的那几条 |
| 交接 | 交给开发 | 就绪检查会用人话告诉你差什么，齐了就能导出 ZIP 交接包 |

右侧的 Demo 是桌面和手机两个真实视口。需求或架构一变，它自动重播一遍动画 —— 「加了这个，用户会看到什么」这件事，不用再靠脑补。

## 我比较在意的几个细节

**它会先问你，而不是先给你一坨方案。** 你写「读取另一个会话里的开发进度并继续」，它会先告诉你：这是操作指令，不是产品需求，我需要哪些材料才能继续。而不是自作主张给你生成一份「读取会话功能」的需求 —— 这种事我踩过，很难受。

**说错了可以退。** 改错层级、删错节点，右上角能撤销；删除节点前它会告诉你「会连子需求一起删」。

**候选不等于已采纳，采纳不等于已批准。** 三段是分开的，每一段都得你亲手点。

**能拿出去。** 需求可以一键导出 Markdown，粘进飞书、钉钉、Notion 就能开会；审批冻结后能导出带离线 Demo 的 ZIP。

## 现在到什么程度

我尽量说实话，因为「代码里有」和「你屏幕上真的能用」是两件事。

- 单元测试 93 项、类型检查、构建、独立的浏览器 Demo 测试都过。
- 下面这些我在真实运行的 Harness 界面上点过：侧栏入口、建项目、需求树的增删改与拖拽、优先级与双端验收、需求依赖（成环会被拒并点名是哪个节点）、撤销重做、参考来源与功能对照矩阵、双端 Demo 的交互与保存、版本差异与字段级部分批准、交接就绪检查和 ZIP 导出、开发会话派发与报告回传（在隔离夹具里跑通的，不是批准你的真实产品）。
- 真实模型也跑过：理解卡、候选方案生成、拒绝候选再来一次、静态 REA 研究。但这些只验证了走过的那条路，别当成「所有格式、所有情况都支持」。
- 还没做好的：整站抓取（现在只读你指定的 URL）、完整的实现证据关系图、多页大结果的展示。还没有正式 Release，也没发 npm。

## 装一下试试

当前基线：Node.js 24、DeepSeek Harness `0.2.2-rc.1`、Cordis 4.1.x。别的版本没验过，别硬上。

```sh
npm ci --include=dev --ignore-scripts
npm run build
npm run typecheck
npm run test:unit
```

然后在 Harness 的插件管理器里安装**本目录的绝对路径**（别手工改 profile）。装完如果提示「已安装」，按管理器说的先移除再重装，别删项目数据。

改过 Host 侧代码的话，记得重启 Harness 再刷新页面 —— 只重载客户端不够，这点我踩过好几次坑。装完别只看「安装成功」的提示，回界面点几下确认。

## 五分钟上手

1. 左侧栏点「创意工坊」，第一次进来是项目列表和三步引导。
2. 「新建项目」，在「想法」里写一句你想解决的问题 —— 别写 PRD，一句话就行。
3. 等它回一张「理解卡」：它觉得你要做什么、还缺什么、有什么要你答。答完点「确认理解，开始推导」。
4. 候选方案不会自己跑进草稿。你看过内容和 Demo，点「采纳」才进。
5. 然后需求 → 架构 → 审批（冻结 v1）→ 交接（检查就绪、导出 ZIP）。

想看别人怎么做的：需求阶段可以手工登记参考产品，把它的功能列成对照矩阵；也可以让 AI 读公开来源做研究（会提示可能产生的模型费用）。

## 边界

AI 只给候选，采纳和批准永远是你点。研究启动时会把参考内容发给所配置的模型，只研究你有权研究的材料。模型的话是推断 —— 工具没抓到、抓失败、结果未知的部分，它不会替你抹平。

Demo 是交互原型，不是生产系统。派发开发要你明确确认目标工作区；「已提交」只代表对方收到了，会话空闲也不代表活儿干完了。结果不明的时候我不会偷偷重试第二次。

仓库里没有用户项目、聊天记录、Host 配置、凭证或私有参考。也别把自己的 Cookie、令牌、产品数据提交进来。
